imapvault

Getting started

From install to a backup you have restored once. imapvault only reads your mailbox until step 11, and restore only ever adds mail, so you can stop at any point before that and nothing on your server has changed.

1. Before you start

You need a mailbox on Fastmail, Gmail, or another IMAP server. Microsoft 365 and Outlook.com are not supported: Microsoft does not offer app passwords for IMAP and only allows it through OAuth2, and imapvault signs in with a password only.

You also need an app password: a separate password your provider creates for one application, so imapvault never sees your real one. It can be revoked on its own.

  • Fastmail: Settings, Privacy & Security, Integrations, New app password, access "Mail (IMAP)".
  • Gmail: myaccount.google.com/apppasswords. It needs 2-Step Verification, IMAP must be switched on in Gmail's settings, and Google Workspace admins can switch app passwords off.

Decide one thing now: whether the repository is encrypted. It is fixed when the repository is created and cannot be added later, so step 3 comes before step 6.

imapvault is a new project. Backup only reads your mailbox, and restore only adds mail, but restore has only been run against a test server, so try it on a throwaway account before you rely on it.

2. Install

curl -fsSL https://imapvault.sh/install.sh | sh
imapvault --version

This puts imapvault in ~/.local/bin, so make sure that is on your PATH. For other ways to install (Homebrew, archives, a container), see the install section.

3. Make a key

imapvault encrypts to a public key, so the machine that makes backups never holds anything that can read them. Make a key pair on a machine you trust:

imapvault keygen --out personal.key

Wrote the private key to personal.key (mode 0600).
Back it up somewhere safe: without it the repository cannot be read.

Public key (recipient): age1nc47px2whqdrl09m73f75cdqsvg0njf0svpnrd6lxdl86mgt547sacaxan

Add to your account config:

  [encryption]
  recipients = ["age1nc47px2whqdrl09m73f75cdqsvg0njf0svpnrd6lxdl86mgt547sacaxan"]
  identity_file = "personal.key"   # only on machines that read mail; a backup-only machine omits it

Keep personal.key safe, and make a second key the same way as a recovery key and keep it offline: without a private key the repository cannot be read, and there is no way around that. Put both public keys in the config below. If you would rather not encrypt, skip this step and leave [encryption] out, knowing it cannot be changed later.

4. Write a config

imapvault reads one TOML file per account, in ~/.config/imapvault/NAME.toml, and you pick the account with --account NAME. Start from the example for your provider in examples/ on GitHub (Fastmail, Gmail, or any IMAP server). Save this as ~/.config/imapvault/personal.toml:

[imap]
host = "imap.fastmail.com"       # Gmail: imap.gmail.com
username = "you@example.com"

[repository]
path = "~/imapvault/personal"

[folders]
exclude = ["Spam", "Junk"]

[encryption]
recipients = ["age1workingkey...", "age1recoverykey..."]   # the two PUBLIC keys from step 3
identity_file = "~/.config/imapvault/personal.key"         # only on a machine that reads mail

The password never goes in the file. For now, put it in the environment:

export IMAPVAULT_IMAP_PASSWORD='your-app-password'

For anything unattended, add password_file = "~/.config/imapvault/personal.password" (one line, chmod 600) or a password_command under [imap] instead.

On Gmail, do not exclude [Gmail]/All Mail. Gmail shows labels as folders, and archived mail (the Inbox label removed) exists only in All Mail, so leaving it out would miss that mail, and archiving a lot at once would look like a mass deletion. A message is still stored only once, but the first backup downloads it once per label, and Gmail limits how much IMAP data an account can download per day, so a big first backup can take several runs. Excluding [Gmail]/Spam is safe.

A machine that only makes backups (a NAS, a server) should leave identity_file out: it can then back up, tidy up and verify, but cannot read a single message. Reading, diffing and restoring need the private key, so do those from the machine that has it.

5. Check the connection

imapvault --account personal doctor

doctor logs in, shows what the server supports, and lists every folder with its message count and whether it will be backed up. It changes nothing and needs no repository yet. This is what it printed against the test server:

Server features:
  CONDSTORE    yes  fast flag-change detection
  QRESYNC      yes  fast expunge detection
  OBJECTID     no   skip downloading a message already stored (not used yet)
  SPECIAL-USE  yes  folder roles such as \Trash and \Sent
  UIDPLUS      yes  needed by restore

Folders:
  FOLDER        MESSAGES  ROLE     BACKED UP
  Archive       2                  yes
  Archive/2025  1                  yes
  Drafts        0         \Drafts  yes
  INBOX         4                  yes
  Junk          0         \Junk    no (excluded)
  Sent          1         \Sent    yes
  Trash         1         \Trash   yes
  Tricky        4                  yes

13 message(s) in the folders that would be backed up.

CONDSTORE and QRESYNC make later backups fast. Without them imapvault still works, but it has to list every folder in full each time.

6. Create the repository

imapvault --account personal init

This creates the repository at repository.path and ties it to this account, so no other mailbox can be written into it by mistake. It prints whether the mail will be encrypted. If it says NOT encrypted and you meant it to be, fix recipients and delete the repository now: this is the last chance.

7. Make the first backup

imapvault --account personal backup

The mailbox is opened read-only: folders with EXAMINE and messages with BODY.PEEK[], so nothing is marked as read and nothing on the server can change. The first run downloads everything and can take hours; if it is interrupted, the next run continues where it stopped. In a terminal you see a live progress line; in a log you see plain lines, ending with a summary:

Archive [1/7]: fetching 2 messages (521 B)
Archive [1/7]: done, full, 2 messages, +2 -0 ~0 (521 B in 0s)
...
Snapshot 1: 13 messages in 7 folders
  messages  +13 new, -0 deleted, ~0 flag changes
  storage   12 blob(s) written (2.7 KiB), 1 already stored
  read      13 body(ies) downloaded; folders: 0 unchanged, 0 incremental, 7 full
  folders   +7 new, -0 gone

Run it again straight away and it reads nothing: each folder the server reports as unchanged costs one EXAMINE.

8. Look around

Every backup is a snapshot: a cheap index of what was where, with flags. Reading names and headers needs your private key, so run these where identity_file is set.

# your snapshots
imapvault --account personal snapshots

# the folders in the newest one, then the messages in one folder
imapvault --account personal ls latest
imapvault --account personal ls latest INBOX

ls latest INBOX prints one line per message, ending with a hash you can give to show:

Snapshot 1 (2026-11-24 18:26:55), folder INBOX
UID  FLAGS  SIZE  DATE              FROM                SUBJECT        SHA256
1           224   2026-05-03 11:00  alice@friends.test  Hello          66d846875c8b
2           241   2026-05-04 12:30  bob@work.test       Meeting notes  847413d88260
...

imapvault --account personal show 3f9a1c2b7d4e

# what changed between two snapshots
imapvault --account personal diff latest~1 latest

9. Keep it running

A backup you have to remember to make is not much of a backup. The simplest way to keep one going is run:

imapvault --account personal run

run backs up every hour, applies your retention policy daily, retries failures with a back-off, keeps going after an alert, and tells you if backups stop working. It never prunes unless you ask (--prune-every 7d). Stop it with Ctrl-C or SIGTERM and it exits cleanly.

On a NAS or home server, the Docker guide has a Compose file that starts it with docker compose up -d. If you would rather use cron or a systemd timer, see the scheduling notes. Use one or the other for an account, not both.

10. When the guard trips

Each run is compared with the one before. If a lot of mail has disappeared from the server, or a folder has vanished, the snapshot is flagged, the last good one is pinned so it cannot be pruned, and backup exits with code 3. Here 80 of 113 messages were deleted from one folder:

Snapshot 4: 33 messages in 8 folders
  messages  +0 new, -80 deleted, ~0 flag changes
  storage   0 blob(s) written (0 B), 0 already stored
  read      0 body(ies) downloaded; folders: 7 unchanged, 1 incremental, 0 full


ALERT 1 (mass-deletion): 80 of 113 messages deleted (70.8%) since snapshot 3: Bulk 80
  snapshot 4 is flagged; snapshot 3, the last one before it, is pinned and kept
  see what changed:  imapvault --account personal diff 3 4
  acknowledge:       imapvault --account personal ack 1

Look at what happened, then decide:

imapvault --account personal alerts
imapvault --account personal diff 3 4

# when you have dealt with it
imapvault --account personal ack 1

Until you acknowledge an alert, prune refuses to run. To be told without watching a terminal, set on_alert_url to a URL that accepts a text POST (an ntfy topic, for example) or on_alert to a command; see the guard section of the README.

11. Get mail back

Restore is the only command that writes to your server, so it cannot write until you have seen exactly what it will do and approved it. First allow it in the config of the account you restore into:

[restore]
allow_append = true

Then ask for what you want. This brings back everything deleted from the server in the last day, as new folders next to your own. The first run only previews:

imapvault --account personal restore --deleted-since 1d

Restore preview. Nothing has been written yet.

  Source:  deleted within 24h0m0s
  Mode:    into new folders under "Restored/deleted-2026-11-24", next to your own

  FOLDER                            STATE                 ADD  SKIP (already there)
  Restored/deleted-2026-11-24/Bulk  new: will be created  80   0

  Will create 1 folder and add 80 messages (14.9 KiB). 0 already on the server.
  Nothing is deleted, moved, re-flagged or overwritten on the server.

  Plan token: 0156b-974b8
error: restore needs your approval: review the preview above, then run it again with --confirm 0156b-974b8. Nothing was written

The token is a hash of the whole plan. At a terminal imapvault asks you to type it; in a script, pass it back. If the server has changed since the preview, the token no longer matches and nothing is written:

imapvault --account personal restore --deleted-since 1d --confirm 0156b-974b8

Restored 80 messages (14.9 KiB) and created 1 folder. 0 were already there.

# run it again and it finds nothing to do
imapvault --account personal restore --deleted-since 1d

Nothing to restore: everything selected is already on the server.

Restore only creates folders and appends messages. It never deletes, moves or re-flags anything, never restores the \Deleted flag, and skips any message that is already there, so running it twice is safe. Look through the Restored/ folder in your mail app, then move what you want back, and delete the folder yourself when you are done.

Restore has only been run against a test server. Try it on a throwaway account first, and only then point it at a mailbox you care about.

12. Tidy up

Snapshots pile up, and mail deleted from the server stays in the repository. Only two commands change that, and nothing else ever deletes data:

imapvault --account personal forget
imapvault --account personal prune --dry-run

forget marks the snapshots your [retention] policy no longer keeps; it deletes nothing. prune then removes what no kept snapshot needs, but only once mail has been gone from the server for 180 days by default, and never while a snapshot is pinned or an alert is open. Look first with --dry-run. run does the forget part for you and the prune part only if you ask.

When something is off

  • Login fails (NO [AUTHENTICATIONFAILED]): use the app password, not your account password. On Gmail, check that IMAP is switched on. doctor tests the login without touching anything.
  • "repository is locked": another imapvault command, or run, is using the repository. Wait for it; a second one never runs at the same time.
  • Exit codes: 0 is fine, 1 is an error with a message, 2 means some folders were not reached and the next run finishes them, and 3 is a guard alert (step 10).
  • "Writing to ... is not enabled": restore needs [restore] allow_append = true in the config of the account it writes to (step 11).
  • The first Gmail backup is slow or stops: Gmail limits daily IMAP downloads. Run it again, or leave run going, and it resumes.
  • ls, show or restore cannot read names: they need the private key. Set identity_file on the machine you read from.
  • Mail moved to a folder you excluded: the backup can no longer see it, so it looks deleted. Exclude folders you do not want, and keep the rest.
